## 1. 管理目标与现状依据

提前识别可能影响范围、质量、工作量、工期和成本的不确定事件，确定责任人、预防措施、触发条件及应急方案，持续验证措施有效性，保障核心学习链路和课程交付。

当前项目已有账号、八题前测、四方向二十个单元、方向后测、服务端判分、JSON 进度保存和作答证据画像。DeepSeek 是可选的前测分析服务，学习搭子为本地规则交互。PostgreSQL、RAG、LangGraph 工作流和动态课程尚未落地，不能继续采用“纯前端运行、刷新必丢状态”的旧假设。

以下是已知限制或管理缺口，是识别风险的依据，并非本次已复现的故障：

- JSON 仓储已有文件锁、原子替换和 revision 校验，实际规模下的性能、备份恢复及未来迁移仍需验证。
- 业务测试已存在，但 CI 尚未执行 pytest 与 Vitest；根目录端到端、契约和 AI 评测目录主要为规划说明。
- Docker Compose 已有配置，正式部署仍需环境、HTTPS、安全、备份与回滚验收。
- 原项目进度表及部分早期演示文档落后于当前代码，不能据其状态判断里程碑完成。
- 内容标签、教学效果及真实目标用户可用性仍需验证，画像不能等同于标准化能力测评。

已发生的问题创建缺陷或阻塞 Issue；尚未发生的不确定事件进入风险登记册。例如“CI 未运行业务测试”是已知缺口，“业务回归在合并后未被发现”是对应风险。整改缺口与持续监控风险分别跟踪。

## 2. 识别维度与评估方法

### 2.1 识别维度

| 维度 | 本项目检查内容 |
| --- | --- |
| 资源 | 五人可投入时间、关键人员替补、开发设备、教学审核者、题库及测试材料 |
| 项目管理 | 范围与工作量估计、职责交接、评审、文档一致性、信息安全和验收口径 |
| 外部因素 | 教师与用户反馈、模型服务、云资源、第三方软件、内容许可和审核依赖 |
| 技术 | 前后端契约、判分、JSON 存储、版本迁移、配置、AI 输出与工作流 |
| 进度 | 课程节点、关键路径、集成与回归时间、部署和彩排准备 |

在需求评审、接口/题库/模型变更、PR 评审、缺陷分析、每周例会与发布检查中识别风险。每项描述遵循“由于某原因，可能发生某事件，从而影响某目标”，避免仅写“技术难度大”。

### 2.2 评分与优先权

概率 P 与影响 I 均使用 1—3 分，不解释为统计概率。

| 指标 | 低（1） | 中（2） | 高（3） |
| --- | --- | --- | --- |
| 发生概率 P | 条件较少，已有防护且有验证依据 | 有现实触发条件，验证或保障仍不充分 | 触发条件较易出现，或关键依赖尚无保障 |
| 影响程度 I（重要性） | 局部体验受影响，可以绕过 | 部分功能或质量目标受损，需要返工 | 核心链路、数据可信性、信息安全或里程碑受威胁 |
| 工作量影响 | 额外投入不超过 1 人日 | 额外投入超过 1、不超过 3 人日 | 额外投入超过 3 人日，或涉及跨模块重构/迁移 |
| 进度影响 | 延误不超过 1 个工作日，不影响关键路径 | 延误 2—3 个工作日，可在阶段内调整 | 延误超过 3 个工作日，或直接威胁里程碑 |
| 成本影响 | 可在已批准资源内消化 | 需重新分配预算或增加有限资源 | 可能超过批准上限，或新增必要支出尚无资金安排 |

“进度/成本”分别填写，避免以低现金支出掩盖人力和工期影响。实际预算尚未批准时，金额风险保留“待预算确认”，不把架构报告中的候选费用当作承诺。

风险值 **S = P × I**：6—9 为高，3—4 为中，1—2 为低。紧急程度另外判断：

- **P0（立即处置）：** 已发生泄露、数据损坏或当前演示/发布被阻塞，立即通知 D/A/E，先控制影响，按事故处理。
- **P1（本轮优先）：** 高风险，或中风险将在下一里程碑前触发；当日确认负责人，下一工作日形成行动与期限，处置期间每日检查。
- **P2（计划处理）：** 尚未临近触发的中低风险，纳入迭代，每周检查；相关功能启用或外部条件变化时立即重评。

严重性与紧急性分开记录，后续功能的风险先审准入条件和排期。已有防护不等于风险自动关闭；日常检查可异步更新，周会集中重评。

| R13 | PR 仅附 CI 绿灯；需求无用例映射；跨系统流程出现遗漏故障 | 减轻：E 建 FR/NFR—用例—结果映射，D 补 pytest/Vitest CI；补关键端到端和 AI 评测。门禁补齐前，相关 PR 手动提交业务测试结果，失败不得合并 | 下一次功能合并前落实手动证据，正式发布前完成关键跨系统与 AI 质量验收；报告含版本、环境、失败项和复测 | 已知门禁缺口，待整改 |
| R14 | 拟修改版本 1 题义/选项顺序；来源 ID 变化；规则变更但版本未更新 | 规避与减轻：冻结已有版本含义，新增内容/评分版本及迁移方案，保留提交快照和来源 ID。异常时停止发布，以版本识别历史记录并恢复正确解释 | 内容/评分合并前；B 审内容、D 验迁移，覆盖旧记录、来源去重、过时提交拒绝与历史画像对照 | 持续监控 |
| R15 | 测试前一周仍无审核者、对象或时间；反馈样本不足 | 减轻：B/E 提前预约成年学习者、教学审核者与交叉测试小组，准备任务和备用时段。不足时先组内走查发现缺陷，重排外部验证并说明证据限制 | 测试前一周确认；NFR-8 的 10—15 人与 80% 无指导完成目标按实际记录，不用组内测试冒充目标用户验证 | 待外部资源落实 |
| R16 | 新组件同时进入主线；PoC 缺恢复/幂等证据；检索不足仍生成课程 | 减轻：分阶段做最小工作流，验证合法单元、先修、重复触发、重启恢复和修订冲突；未通过不接主线。失败保留当前有效计划，使用审核课程与规则流程 | 正式接入前通过 PoC 准入；交付成功及失败样例、恢复测试、依赖、工时与继续/延期决定 | 后续阶段，准入待验证 |
| R17 | 无批准额度即扩展调用；费用达上限 80%；重复请求或延迟上升 | 减轻：A/D 确认预算、配额和告警，统计调用、延迟与失败；保留证据缓存，补限流和去重。达到上限暂停可选生成，保留核心学习，不自动重试放大请求 | 扩大调用前明确预算与阈值，有调用时每日记录；80% 为建议预警线，提供超限控制与缓存验证 | 预算待确认，调用规模待测 |
| R18 | 敏感文件入 Git/截图；发现越权；公开环境保留弱演示凭据或 HTTP | 规避与减轻：鉴权、最少数据出站、日志脱敏、密钥检查；公开前处理演示账号，启用 HTTPS/安全 Cookie，补登录限流与删除流程。泄露后立即撤销/轮换凭据、隔离入口、保全证据，再按团队确定的流程清理泄露材料及历史 | 真实用户试用/公开发布前；越权测试、配置检查、数据字段审查、删除验证与应急联系人记录 | 已有基础鉴权，公开部署措施待验收 |

## 5. 外部依赖专项检查

依据课程参考中的三个问题，检查外部投入、输入资料和供应商依赖，不把未落实条件写成已有资源。

| 检查问题 | 本项目依赖 | 责任人与检查时点 | 缺失时的处理 |
| --- | --- | --- | --- |
| 是否依赖外部组织的投入、决策或批准？ | 课程反馈、学习者招募、教学审核、部署资源与经费；如开展机构要求审核的研究，需确认相应流程 | A 协调、B/E 跟进；里程碑与试用前 | 记录请求日期、答复期限、影响及替代方案；未落实前采用合成数据与内部验证，不声明已获批准或完成外部验收 |
| 系统概述、测试用例等输入是否可用且充分？ | 需求/架构已有但部分过时；单元和集成测试已有，跨系统及 AI 评测不充分；教学标签与许可需审核 | D/E 核对需求到用例，B 核对内容；验收及发布前 | 缺失输入建任务，明确补齐标准与责任人；不能因已有目录或文档标题就判定就绪 |
| 是否高度依赖供应商或第三方软件？ | 可选 DeepSeek、npm/Python 依赖、Docker 镜像及未来部署平台；RAG/记忆/编排为后续依赖 | D 在安装、升级、模型变更与部署前验证 | 固定已验证版本并保留配置和构建说明；模型失败停用建议、保留课程；关键依赖故障使用已验证环境或回滚版本 |

当前未发现已签约的分包安排，不假设存在供应商 SLA、教学审核承诺或已获批预算。供应商价格、型号和额度在实际接入评审时核实，不以旧调研数字作为现行事实。

## 6. 监控、升级与关闭流程

1. **登记：** 发现者当天提供原因、事件、后果、证据与建议负责人，A 分配风险 ID。已知缺陷单独建 Issue，并与风险关联。
2. **评估：** 责任人与相关成员评估 P、I、工作量、工期、成本、触发条件和优先权；未确认费用与人员能力保留假设，不编造精确概率或金额。
3. **计划：** 明确规避、减轻、转移或接受策略。当前以规避和减轻为主，不假设供应商承担风险；接受残余风险须记录理由、边界、应急措施与复核日期。
4. **执行：** 措施拆成任务，记录人员、截止与依赖；触发后立即重评。P0 走事故流程，P1 不等下周例会，P2 每周检查。
5. **沟通：** 按[沟通计划](communication_mgmt_plan.md)报告。值守期间 P0 目标 30 分钟响应；P1 当日确认、下一工作日形成行动计划。阻塞半个工作日由 A 协调，影响里程碑时同步全员及教师。
6. **验证：** 实现者提交测试、审核、恢复或演示证据，非作者复核。措施完成后重新评分残余风险，不能仅以“代码已写”为关闭依据。
7. **关闭或接受：** 触发条件消失且证据通过方可关闭；持续存在的供应商、安全风险维持监控。接受残余风险须记录团队评审结论、接受人和期限，范围变化后重新打开。严重越权、明文凭据、数据损坏不得以接受风险替代发布质量门。

登记状态采用：待评估 → 待处置 → 处置中 → 待验证 → 持续监控／已接受／已关闭。第 4 节的“已有保护”“待验收”等为当前说明，首次评审时补充正式状态与日期。

**单项跟踪模板：** 风险 ID / 发现日期 / 阶段 / FR/NFR 与 Issue / 原因—事件—后果 / P、I、S 及优先权 / 负责人和复核人 / 行动与截止 / 触发证据 / 验证结果 / 残余评分 / 接受或关闭结论 / 下次检查日期。

| 展示前 2 天至当天 | R01/R03/R05/R07/R09 | 冻结范围、主备人员、双服务启动、能力口径、录屏与备用环境 |
| 运行维护与阶段复盘 | 全部未关闭风险 | 每周更新风险变化、措施逾期、事故原因及残余风险，形成改进项 |

以上性能与成功率是[非功能需求](../requirements/nonfunctional_spec.md)中的验收目标，需在约定环境与负载下测试，不代表已有实测结果。原型演示不替代完整 MVP 的发布验收。

A 在排期时建议预留每轮可用工时的 15% 用于联调、风险处理及回归，按五人实际容量确认，不作为既有预算承诺。备用准备包括可复现代码版本、合成演示数据、当前版本录屏、配置说明和经验证的备份。代码回退涉及数据格式变化时，应同时验证数据兼容性，不直接覆盖当前真实数据。

计划每周更新；需求、题库版本、AI 服务、存储或部署环境重大变化时即时更新。保留风险编号和处置历史，结论以证据为准。
