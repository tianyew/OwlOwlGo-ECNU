## 2. 工具和第一版结构

沿用仓库规划的PostgreSQL 17、SQLAlchemy 2、psycopg；补Alembic管理版本化DDL。首版沿用现有同步FastAPI处理方式，不同时改为异步数据库框架。数据库事务使用显式提交/回滚边界；迁移脚本纳入版本控制。[SQLAlchemy事务说明](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html)、[Alembic迁移说明](https://alembic.sqlalchemy.org/en/latest/tutorial.html)。

| 数据 | 建议结构与负责人 | 边界 |
| --- | --- | --- |
| users、sessions | A：用户主键、规范化用户名唯一约束、密码哈希；会话仅存token摘要及有效期，关联用户 | 迁移旧用户保留ID及哈希；导入不复制有效旧会话，要求重新登录；SQL运行后的普通重启不应使合法会话失效 |
| learning_progress | A：user_id唯一、revision、assessment_epoch、JSONB状态及必要历史归档 | 草稿/方向/页面状态可先用JSONB；更新受事务与revision约束；不能靠JSONB绕过业务校验 |
| submissions | A：按用户与submission_id约束唯一，显式quiz_id、版本、时间，JSONB保存完整历史判分/题目快照 | 单独逐条存储，避免把所有历史提交塞回一整个用户文档；不同用户的同UUID按既有用户域语义隔离；同用户复用ID换测验/答案拒绝 |
| 历史AI分析及归档 | A保留当前分析及legacy_progress；B定义diagnoses与关联分析结果模型 | 保留provenance和旧版本，不把旧客户端成绩升级为可信正式证据；不可变诊断证据与可追加AI分析分离 |
| learning_preferences、plans、plan_revisions | C建模、迁移、仓储与测试 | 本人版本、诊断/偏好来源版本、唯一生效计划及接受幂等约束 |
| intervention_preferences、practice_sessions、intervention_events | D建模、迁移、仓储与测试 | 用途绑定、用户隔离、事件幂等；不写入正式成绩或证据 |
| 画像与复习队列 | E通过仓储读取正式记录后计算 | 首版不额外持久化一份容易不一致的派生结果；后续有性能证据再加缓存 |
| 课程/题库/模板 | B/E维护有版本的静态内容与审核白名单 | 允许继续使用只读JSON作为内容资产；冻结历史版本，不等同于继续用JSON保存用户数据 |

先完成最少必要的关系约束，历史结果保留快照；无需本轮把全部题库、认知标签和课程正文都规范化为几十张表。

## 4. 必须守住的原有行为

1. 一次正式提交的结果插入、进度更新、revision变更在同一事务中提交；任何一步失败全部回滚。
2. 同一用户、同一submission_id、同一内容返回原结果；换答案或换测验必须冲突。两个并发重试只能产生一个正式提交；唯一约束不能只靠先查后写实现。
3. 幂等重试先按既有业务规则识别原提交，不能被过时revision误拒；同用户不同新提交使用相同旧revision竞争时最多一个成功，另一个冲突。
4. 通过记录、重测epoch、题目来源去重、旧provenance、草稿、当前AI分析与内容/评分版本均保留；不能因迁移重新判所有历史数据而改写结果。
5. 不再以JSON文件锁保障SQL并发；使用数据库事务与约束，并测试行锁/乐观更新策略。保留现有API行为与隔离语义，新增接口另行版本化。
6. 数据库断连时返回可恢复错误，不静默改写JSON作为备用存储，否则会分裂成两套数据源。

## 5. JSON历史数据迁移与回退

这是实施阶段流程，不是本次已执行的操作。不得直接覆盖当前真实数据。

1. **复制与预检**：先在脱敏副本演练。验证schema、用户关联、唯一ID、版本和JSON可解析性；输出错误清单。只读预检不改源文件。
2. **兼容解释**：复用已确认的legacy规则形成待导入快照，保留原归档和来源标签；列出无法解释条目，不能静默跳过。
3. **导入空目标**：先用户后关联数据；标记导入批次/源摘要。重复执行相同快照不重复创建记录；同ID内容不同停止并报告，不能直接覆盖。部分失败回滚或明确可重跑的批次状态。
4. **对账**：按用户核对账号、正式提交数、草稿、revision/epoch、通过记录、当前分析和画像；不仅比较总行数。保留脱敏对账报告。
5. **切换前冻结写入**：演练通过后安排短暂停写，备份源文件，生成最终快照重新导入/对账，禁用旧实例写入，切换应用配置。禁止新旧后端同时对不同存储接受写入。
6. **切换验证**：账号重新登录、保存草稿、正式提交、刷新和重启检查；确认新写入仅进入SQL。SQL连接失败即失败，不自动回退JSON。
7. **回退条件**：新系统尚无新增业务写入时，可停止SQL应用后恢复冻结的JSON版本；已经接受新写入时，不能直接切回旧JSON。必须先停写、保全SQL备份并修复SQL恢复，或验证能够导回全部增量的方案；无法对账时保持暂停，不能丢弃新数据。
8. **数据库恢复演练**：用pg_dump生成备份，在独立空库用pg_restore恢复，运行对账与主流程验证；只有生成文件没有恢复验证不算完成。[PostgreSQL备份工具](https://www.postgresql.org/docs/17/app-pgdump.html)、[恢复工具](https://www.postgresql.org/docs/17/app-pgrestore.html)。
