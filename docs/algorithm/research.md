## 3. 研究问题：怎样让模型按教学要求提供帮助？

**对应 PPT 第 3-4 页；论文 §1、§3.1，PDF 第 1-3 页。**

通用大语言模型能够解释概念、生成代码并开展多轮对话，但教学场景还需要控制回答的范围和方式。主要问题包括：

- **超出课程范围**：回答可能引入当前课程不涉及、学习者也难以理解的知识。
- **过早给出答案**：学生拿到完整解法，却没有经历必要的思考过程。
- **表达不适龄**：回答的语言、长度和复杂程度不一定适合中学生。
- **帮助不够贴合任务**：模型可能给出泛泛的解释，未解决学生当前的具体困难。

因此，论文同时处理两类约束：

| 约束 | 需要解决的问题 | 主要设计手段 |
| --- | --- | --- |
| 课程内容约束 | 可以依据什么材料回答？讨论哪些主题？ | 预先整理的课程知识库与文件检索 |
| 教学行为约束 | 什么时候给提示？怎样解释？是否展示完整答案？ | System Prompt、内容语义标签与分层帮助策略 |

系统还要求跨设备访问、无需学生登录注册、支持连续问答与实时反馈。作者的总体路线是复用现有模型，通过资料组织和提示工程配置教学行为，无需重新训练或微调模型。

## 4. 技术路线：把各个技术点串起来

### 4.1 先区分准备阶段与使用阶段

**对应 PPT 第 4-11 页；论文 §3，PDF 第 3-5 页。**

**准备阶段：**

1. 按学习模块整理 Markdown 课程文件。
2. 用标题区分任务、提示、解释、答案等教学用途。
3. 上传课程文件，配置文件检索工具。
4. 编写系统提示词，规定课程范围、回答语言及教学方式。

**学生提问后的处理逻辑：**

1. 前端接收问题，后端负责请求转发和会话管理。
2. 系统结合问题和前文，判断学生需要哪类帮助。
3. 通过 `file_search` 查找相关课程内容。
4. 模型结合检索材料、教学指令和会话上下文组织回答。
5. 生成的文本逐步返回网页。
6. 学生继续追问时，同一对话线程提供之前的交流背景。

这是根据论文描述整理的**逻辑过程**。论文没有公开足以复现全部细节的函数调用顺序，也没有说明上述每一步都对应一个独立程序。

### 4.2 三层架构：谁负责什么？

**对应 PPT 第 5 页；论文 §3.2，PDF 第 3 页。**

| 层次 | 采用的技术 | 主要职责 |
| --- | --- | --- |
| 网页前端 | React、Next.js、Chat UI Kit React | 让学生输入问题，展示聊天记录和逐步返回的回答，支持不同设备 |
| 后端 | Next.js API routes | 安全处理 API 密钥，管理会话与对话线程，转发前端和模型服务之间的消息 |
| AI 层 | GPT-4o、Assistant API、课程文件工具 | 结合教学指令、检索内容与上下文，生成回答 |

**几个容易混淆的名称：**

- **GPT-4o**：理解问题和生成回答的模型。
- **API**：软件之间调用功能的接口。
- **Assistant API**：论文使用的接口名称，官方名称通常写作 Assistants API，用于配置和使用助手的模型、指令、工具及对话功能。
- **`file_search`**：助手可使用的文件检索工具。
- **Thread**：把同一次聊天中的消息关联起来的对话记录。

同一个 Next.js 框架可以同时用于组织前端网页和提供后端接口。因此，前端与后端都出现 Next.js，并不意味着它们承担相同职责。

本文按论文当时的实现解释接口名称，不将旧接口描述当作当前新项目的开发指南。

### 4.3 知识库：六类标签怎样组织？

**对应 PPT 第 6 页；论文 §3.3、Figure 1，PDF 第 3-4 页。**

课程内容按学习模块拆成多份 Markdown 文件。每份文件使用统一的二级标题 `##`，将内容划分成不同教学功能。

| 标题 / 语义标签 | 作用 | 以“判断偶数”练习说明 |
| --- | --- | --- |
| `Tasks` | 保存任务要求 | 编写判断数字是否为偶数的函数 |
| `Hints` | 提供下一步线索 | 提醒考虑取模运算 |
| `Explanations` | 解释概念和原理 | 说明偶数除以二时余数为零 |
| `Solutions` | 保存参考解答，明确标记禁止直接展示 | 完整参考实现 |
| `Motivation` | 提供鼓励和阶段性反馈 | 在概念理解取得进展时给予鼓励 |
| `Misconceptions` | 保存常见错误理解及澄清 | 帮助纠正对问题或运算的错误理解 |

结构示意如下，具体中文内容用于辅助理解：

```markdown
## Tasks
练习要求。

## Hints
下一步线索。

## Explanations
概念和原理解释。

## Solutions (do not show)
参考解答，禁止直接展示。

## Motivation
鼓励性反馈。

## Misconceptions
常见错误理解及澄清。
```

这里的“标签”主要指**通过标题表达内容的教学用途**。标签告诉模型“这段内容是什么”，教学指令再告诉模型“应该怎样使用它”。

论文说明了文件结构和用途，但没有详细交代由谁标注、全部人工还是有自动化辅助，也没有报告完整的标注规范或一致性检查。不能据此声称作者开发了自动打标签算法。

Figure 1 使用英文示意，正文说明原研究中的术语使用德语。图中的英语回答要求与正文存在差异，解释实际系统时应以 §3.4 和最终 Prompt 的德语要求为准。

### 4.4 file_search 与自适应回答

**对应 PPT 第 7 页；论文 §3.3-§3.5，PDF 第 3-5 页。**

`file_search` 为上传的课程文件提供查找入口。作者复用接口提供的文件检索能力，因此省去了自行搭建外部搜索基础设施的部分工作，但系统仍然有检索过程。

论文把自适应内容组装概括为三个环节：

| 环节 | 含义 |
| --- | --- |
| 意图匹配 | 判断学生是在寻求提示、要求澄清，还是探索概念 |
| 标签检索 | 定位与问题相关、教学用途也适合的课程片段 |
| 回答构建 | 结合材料、教学策略和对话上下文组织回复 |

**“自适应”指回答会根据学生的当前需求和已有交流，调整内容类型与帮助深度。** 可以用同一道题的不同追问理解：

| 学生的需要 | 可以采用的材料与回答方式 |
| --- | --- |
| “我不知道下一步怎么写。” | 利用 `Hints` 提醒学生思考取模运算，先给线索 |
| “为什么要看余数？” | 利用 `Explanations` 解释偶数与余数为零的关系 |
| “我仍然不理解。” | 结合前文补充具体数字的例子，将解释讲得更细 |

上面的中文追问是根据论文机制整理的说明性例子，不是实验记录。

需要区分两个职责：`file_search` 查找相关材料，模型结合材料、指令和历史组织回答。论文未报告独立的意图分类器、确定性的标签过滤引擎，也未给出底层切块、排序或召回参数。

### 4.5 System Prompt：怎样把材料用于教学？

**对应 PPT 第 8 页；论文 §3.4、Prompt 1，PDF 第 4 页。**

System Prompt 是预先给模型配置的角色和行为要求。论文的主要要求包括：

- 担任当前课程的 AI 导师，仅使用知识库回答课程相关问题。
- 使用德语，表达符合 14-16 岁学生的理解水平。
- 回答简洁、耐心、友好，并给予鼓励。
- 避免直接提供知识库答案部分的完整解答。
- 使用提示、引导性问题和分步骤帮助，支持学生自主思考。

标签与提示词的关系是：

> **标签说明材料的用途，提示词规定材料的使用方式。**

具体教学策略包括：任务求助时优先提示，概念问题先解释再类比，出现误解时帮助澄清。所谓“支架”，就是帮助学生继续完成任务的分步骤支持；“苏格拉底式提问”，则是通过引导问题让学生自己说出理由和下一步。

作者通过迭代提示词处理回答冗长、帮助过度及幻觉等问题。这是在调整模型收到的指令，没有更新模型权重。

### 4.6 Thread：多轮对话怎样接上前文？

**对应 PPT 第 9 页；论文 §3.5、Figure 2，PDF 第 4-5 页。**

Thread 保存同一次对话中的历史消息。学生只说“我还是不懂”时，系统可以结合前面的任务和提示，理解这句话指向什么。

Figure 2 用蜜蜂数据问题展示三轮连续指导：

1. 询问蜂群崩溃失调（CCD）的含义，系统使用概念材料解释。
2. 询问如何分析种群数量，系统提供散点图、趋势和异常值等分析提示。
3. 询问单个蜂箱数量归零是否足以支持判断，系统利用误解材料澄清推断。

这里是两种机制在配合：**Thread 提供之前聊了什么，课程材料和教学指令决定当前怎样提供帮助。**

这种个性化主要来自当前会话中的提问与进展。论文未建立跨课次的长期学习者档案，也未说明会话数据保存、标识与删除的具体实现。免登录不等于没有会话状态或完全不保存消息。

### 4.7 Streaming：回答怎样实时展示？

**对应 PPT 第 10 页；论文 §3.6，PDF 第 5 页。**

系统使用流式接口，将生成的文本逐 Token 返回。Token 是模型处理文本的小单位，不一定对应一个汉字或完整单词。网页上的效果是：文字在生成过程中逐步出现，学生可以更早开始阅读。

它与三层架构的关系是：模型生成内容，后端承接消息转发，前端持续更新聊天界面。

作者认为这种方式能够减少感知等待、形成更自然的对话节奏并帮助维持注意力。但第三章没有给出首段出现时间、总生成耗时或注意力的对照实验，不能把这些预期收益当作量化验证结果。

### 4.8 从软件工程角度理解这套方案

**对应 PPT 第 11 页；论文 §3.7，PDF 第 5 页。**

| 设计 | 论文强调的工程价值 | 小组提出的后续检查问题 |
| --- | --- | --- |
| 模块化 Markdown | 内容可检查、可更新，新增课程不必重训模型 | 更新后是否仍引用旧材料？ |
| 教学标签与提示词 | 内容用途与回答策略之间的关系较易解释和调整 | 是否越界回答、泄露答案或跨轮违反规则？ |
| 复用现有模型和文件工具 | 降低自建模型和基础设施的工作量 | 调用成本、接口依赖和异常处理如何管理？ |
| Thread 与 Streaming | 支持连续交流和逐步可见的反馈 | 上下文是否合适，会话数据如何保存与删除？ |

右列是小组工程分析，不是论文已完成的测试。原文使用了“消除幻觉”等较强表述，但没有提供零幻觉的系统测试证明。汇报时应区分设计目标、作者主张与实测证据。

## 5. 评价方法与主要结果

### 5.1 研究怎样开展？

**对应 PPT 第 12 页；论文 §4.1-§4.2、Table 1，PDF 第 5-6 页。**

- 共 13 名参与者：6 名教师或师范生、7 名学习者。
- 教师平均年龄为 32.5 岁，学习者平均年龄为 23.7 岁，与目标中学生存在差异。
- 使用者在自己的设备上体验原型约 30-45 分钟，然后填写问卷和开放式问题。
- 采用 TAM 启发的五点量表，1 分表示强烈不同意，5 分表示强烈同意。
- 开放式问题了解使用困难、改进建议、帮助有效或无效的情境，以及对未来教学应用的看法。

TAM 即技术接受模型，本文重点考察：

| 缩写 | 中文含义 | 可以怎样理解 |
| --- | --- | --- |
| PU | 感知有用性 | 用户觉得系统有没有帮助？ |
| PEOU | 感知易用性 | 用户觉得系统是否容易理解和操作？ |
| IU | 使用意愿 | 用户是否打算或预计以后使用？ |

评价主要回答用户接受度与主观体验问题，没有设置客观学习前后测、延迟测验或学习效果对照组。

### 5.2 PPT 选取的五个问卷题项

**对应 PPT 第 13 页；论文 Table 3，PDF 第 7 页。**

以下都是五分制下的**具体题项均值**，不是系统正确率，也不是各个 TAM 维度的综合总分。所列五项的有效回答数均为 13。

| PPT 中的名称 | 原文题项 | 均值 | 准确含义 |
| --- | --- | --- | --- |
| 整体易用性 | PEOU2 | 4.62 | 认为 AI 导师整体容易使用 |
| 界面清晰度 | PEOU1 | 4.54 | 原题更准确地说是“与 AI 导师交互清晰且容易理解” |
| 感知回答可靠 | PU2 | 4.08 | 认为导师能可靠地回应自己的输入 |
| 使用意愿 | IU1 | 3.85 | 假如可以使用，自己打算使用 |
| 预期使用 | IU2 | 3.62 | 假如可以使用，预计自己将会使用 |

主要观察是：易用性评分较高，未来使用意向评分相对低一些。这反映了该样本对工具的感受，尚不能据此判断长期实际使用行为或学习成绩变化。

### 5.3 r = 0.79 说明什么？

**对应 PPT 第 13 页；论文 §4.3.3，PDF 第 8 页。**

论文报告 **PEOU4 与 IU2 的相关系数 r = 0.79**：

- PEOU4：系统能否顺利按用户的预期工作，该题均值为 3.77。
- IU2：如果能够使用，预计自己会使用。

可以理解为：在这批参与者中，越认为系统按预期工作的人，也越倾向于预计未来会使用。相关关系不能证明因果关系，也不代表模型回答正确率达到 79%。

特别注意：**PEOU4 与上表 PU2“感知回答可靠，4.08 分”不是同一道题。**

### 5.4 用户文字反馈

**对应 PPT 第 14 页；论文 §4.3.4、§5.1-§5.2，PDF 第 8-9 页。**

| 反馈方向 | 主要内容 |
| --- | --- |
| 提问压力较低 | 学习者愿意询问基础问题，能够反复求助 |
| 解释与提示有帮助 | 能获得概念解释、换一种说法的说明，以及误解澄清 |
| 可作为教学补充 | 教师看到补充课程材料和个别指导的潜力，但对实际减负程度仍有保留 |
| 回答有时不够针对 | 部分回复笼统、重复、含糊，或因谨慎而未提供学生期待的帮助 |
| 使用引导需要加强 | 用户希望看到示例问题，更清楚地知道系统的能力和边界 |

这部分提示了一个教学设计问题：帮助太少，学生可能仍然无法继续；帮助过多，则可能替代学生完成关键思考。因此，需要根据具体困难调整帮助方式和程度。

## 6. 论文真正完成了什么？

**对应 PPT 第 15 页；论文 §3-§5。**

1. **系统实现**：把 Web 界面、后端、现有模型及课程文件连接成可运行的原型，提供多轮问答和流式响应。
2. **教学设计**：利用课程分类标题和系统指令，尝试将提示、解释、鼓励和误解澄清用于教学，避免过早直接提供完整答案。
3. **初步评价**：通过 13 人短时体验、TAM 问卷与开放反馈，获得用户接受度和改进方向的证据。

它提供了可复用的系统集成和教学控制思路，但现有证据不足以证明所有约束在各种输入下都稳定执行，也不足以证明学习者已经获得可归因于该系统的学习提升。

## 7. 研究局限与小组分析

### 7.1 作者明确承认的局限

**对应 PPT 第 18 页；论文 §6，PDF 第 10 页。**

| 局限 | 对结论的影响 |
| --- | --- |
| 样本小，且与目标人群不匹配 | 13 名参与者多为成人，难以直接推广到 14-16 岁中学生 |
| 短时、一次性原型体验 | 当时尚未完整接入 RockStartIT 平台，缺少长期使用证据 |
| 个性化能力与行为数据有限 | 缺少长期记忆、多模态输入和细粒度用户建模；未收集交互日志等行为数据 |
| 未明确测量信任校准 | 难以判断学生何时合理采纳、质疑或过度依赖 AI 的回答 |

“信任校准”可以理解为：面对可靠内容能够合理使用，面对可疑回答也会检查，而不是盲目相信或一概拒绝。

### 7.2 小组进一步提出的问题

**对应 PPT 第 19 页；以下是基于全文提出的研究分析。**

- **整体方案相比普通模型有多大改善？** 可以使用相同任务比较普通模型与课程约束版，这就是建立基线。
- **各组件分别贡献了什么？** 可以在其他条件相同的情况下，分别去掉标签或教学规则进行比较，这就是消融分析。
- **约束是否稳定执行？** 需要专门测试课程外问题、反复索要答案、跨轮规则遵循和材料忠实度。
- **是否真正促进学习？** 需要无辅助测验、迁移任务、适当对照及更长期观察，不能只依赖接受度问卷。

这些问题用于说明后续如何补充证据，不应表述为原论文已经完成的实验。

## 8. 对 OwlOwlGo 只保留两点核心启示

**对应 PPT 第 16-17 页；以下均为小组应用建议。**

### 8.1 课程内容与帮助规则分开管理

课程内容回答“教什么”，帮助规则回答“怎样教”。例如：

| 课程内容 | 帮助规则 |
| --- | --- |
| 拼音和声调知识、练习任务、解释与常见误区 | 学生卡住时先给线索，仍有困难时补充解释，按学习进展调整帮助程度 |

这样可以让同一套材料配合不同帮助策略：更新知识内容时更容易找到对应模块，调整提示方式时也可以继续使用已有资料。

### 8.2 记录学习过程，并检验独立完成能力

以声调练习为例，将学习活动组织为：

1. 给出任务与要求。
2. 保留学生第一次作答。
3. 识别具体困难。
4. 按策略提供提示。
5. 学生重新作答，记录修改结果。

初答、提示和再答记录可以帮助理解学生怎样使用了帮助；之后再安排无提示条件下的相似练习，检查能否独立运用所学。

**论文没有完成这一套 OwlOwlGo 学习闭环，也没有验证其学习效果。** 这两点是从论文设计与研究边界中提炼的后续方向。

## 10. 汇报主线的简短概括

本文尝试用结构化课程知识库和教学指令，将通用模型配置成受课程范围约束的 AI 导师，并通过会话上下文和流式输出支持连续交互。13 人的试用显示较好的易用性感受，但规则执行稳定性、长期适用性和实际学习效果仍需要进一步验证。对 OwlOwlGo，最值得借鉴的是分开管理课程内容与帮助规则，并记录学习过程、检验独立完成能力。
